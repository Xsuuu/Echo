# 回声：分阶段开发与 GitHub 分支计划

**项目名称：** 回声  
**开发模式：** 一个可验收功能一个分支，开发完成并测试通过后再进入下一个功能  
**技术栈：** Flutter + Node.js + PostgreSQL，管理后台使用 Vue 3 + TypeScript  
**当前依据：** 《回声-App与管理后台页面功能说明.md》

## 1. 总原则

后续开发按功能分支推进，不按大模块一次性混合开发。

```text
确定当前功能
→ 创建功能分支
→ 开发
→ 本地测试
→ 更新测试记录
→ 提交 PR
→ 验收通过
→ 合并到 develop
→ 开始下一个功能
```

要求：

1. 一个可独立验收的功能对应一个主要分支。
2. 当前功能未测试通过，不进入下一个依赖功能。
3. 数据库变更必须提交迁移文件。
4. App、服务端、后台如果同属一个可验收功能，应放在同一个功能分支里，避免表、接口、页面被拆得过碎。
5. PR 必须写明功能说明、测试步骤、测试结果和已知问题。
6. `master` 只放稳定版本，日常开发合并到 `develop`。

## 2. 分支命名规范

长期分支：

```text
master
develop
```

功能分支：

```text
feature/阶段编号-中文模块-中文功能
```

修复分支：

```text
fix/阶段编号-中文问题
```

示例：

```text
feature/01-应用-骨架
feature/07-粉丝群聊-聊天-列表
feature/13-后台用户-列表
fix/07-粉丝群聊-未读-数量
```

## 3. 优先级说明

当前优先级按产品主链路排序：

```text
基础工程
→ 用户注册登录
→ App 三个底部 Tab
→ 我的和偶像资料
→ 动态基础能力
→ 粉丝群聊
→ 偶像主页和关注
→ 偶像私聊
→ 后台登录和账号管理
→ 后台用户中心
→ 后台内容和运营管理
```

粉丝群聊是消息模块最高优先级。粉丝私聊、系统通知会话、评论详情页不做。

## 5. 阶段 00：仓库和协作基础

目标：先建立能长期协作的仓库结构。

分支：

```text
feature/00-需求文档
feature/00-仓库初始化准备
```

功能：

- 整理并提交项目规划、技术栈、页面功能和阶段计划文档。
- 创建 `master` 和 `develop`。
- 创建 App、服务端、后台和文档目录。
- 创建 `.gitignore`。
- 创建 `.env.example`。
- 创建 README。
- 创建 PR 模板。
- 创建测试记录模板。

验收：

- 仓库结构清楚。
- 敏感配置不会被提交。
- 可以从 `develop` 创建功能分支并提交 PR。

## 24. 合理分支粒度说明

本节是实际开发时使用的分支粒度标准，以本节为准。前文阶段说明用于理解功能归属，本节用于创建 GitHub 分支。

拆分原则：

- 一个分支应该对应一个可以独立验收的产品功能。
- 同一个功能需要的数据库迁移、接口、前端页面、基础校验和测试记录，放在同一个分支里。
- 不建议把“表结构”“接口”“页面”“按钮”拆成多个分支，除非它们是跨多个功能复用的基础能力。
- 列表和详情通常可以放在同一个分支；创建和编辑如果逻辑接近，也可以放在同一个分支。
- 高风险操作可以单独拆分，例如支付、退款、用户状态管理、权限控制、举报处理。
- 后台页面按“一个页面或一组强相关操作”拆分，不按每个按钮拆分。
- 当前分支测试完成并合并后，再进入下一个依赖功能。

合适的分支粒度示例：

```text
feature/05-动态-发布与列表
feature/05-动态-点赞评论删除
feature/07-粉丝群聊-基础会话
feature/07-粉丝群聊-人工智能回复
feature/13-后台用户-列表与详情
feature/13-后台用户-状态管理
```

不建议的过细粒度：

```text
feature/05-动态-表
feature/05-动态-创建-接口
feature/05-动态-创建-页面
feature/05-动态-内容-校验
```

这些应合并为：

```text
feature/05-动态-发布
```
